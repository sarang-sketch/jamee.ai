# Verified values (V1–V22)

This file resolves the design document's **"Values to verify before coding"** table. Every entry
depends on a third-party detail that changes over time, so no other document in this repository
asserts any of these values as fact — they are asserted **here**, with a source URL and a date.

**Fail-loud rule.** If a V-item is `UNRESOLVED`, code must not substitute a plausible value.
It must fail at startup (missing env var, unsupported model, unconfigured constant) so the gap is
visible immediately instead of surfacing as a wrong answer to a farmer. A guess that looks right is
a defect; an honest `UNRESOLVED` is the correct output.

**Method.** Only first-party documentation was consulted: `ai.google.dev` (Gemini),
`console.groq.com/docs` (Groq), `supabase.com/docs` (Supabase), `developers.facebook.com/docs`
(Meta WhatsApp Cloud API), `nextjs.org/docs`, `vercel.com/docs`, `developer.mozilla.org`
(MediaRecorder). Package versions come from the npm registry (`npm view <pkg> version`). Where a
value could not be confirmed on a page that could actually be retrieved, the row says `UNRESOLVED`
and names what specifically is missing and which page was checked.

All rows checked **2026-09-14**.

### Requirement discrepancy — V16 duration ceiling

The requirements assume a **60 second** function duration ceiling. The documented Vercel value on
the target plan is **300 seconds** (Hobby: 300 s default and 300 s maximum, with fluid compute).

Neither number is silently adopted here. The **documented platform value is 300 s**; the
requirements' 60 s is a *self-imposed budget* that sits well below it. That reading is consistent
and the more conservative of the two, but it changes what "the platform ceiling" means anywhere the
design refers to it — most concretely in task 1.2, which sets the per-request soft timeout as a
fraction of the confirmed platform ceiling. Taking a fraction of 300 s instead of 60 s would produce
a very different budget. Recommendation, to be confirmed by the user before task 1.2: keep 60 s as
Jamee's own `maxDuration` export and derive soft timeouts from it, and treat 300 s purely as the
documented hard ceiling that 60 s must stay under.

The requirements' **4.5 MB** body limit assumption **matches** the documented value exactly, so
Requirements 2.7, 3.6 and 10.10 need no adjustment on that axis.

### Source discrepancy — V14 versus V10 on WhatsApp inbound audio containers (resolved, task 22.2)

**The V14 row's original cross-check sentence was wrong and has been corrected in place.** It
asserted that every WhatsApp inbound audio MIME type sits inside V10's accepted container list.
`audio/mpeg`, `audio/mp4` and `audio/ogg` do; **`audio/aac` and `audio/amr` do not** — V10's list is
`flac, mp3, mp4, mpeg, mpga, m4a, ogg, wav, webm`.

Resolved in the only direction this document's fail-loud rule allows: **V10's list is not widened.**
Widening it would assert that Groq accepts `aac`/`amr`, and no first-party Groq page says so — the
accepted-container list on the V10 source page contains neither. "A guess that looks right is a
defect", so the honest output is a refusal the farmer can act on plus a recorded limitation.

What that costs, stated plainly:

- A WhatsApp voice note delivered as `audio/aac` or `audio/amr` is **refused before the media
  download**, the farmer is told to type the question instead, the row is marked `rejected`, and
  nothing is spent. **Requirement 10.6 is not satisfied for those two containers.**
- Closing the gap needs real work — a transcode step ahead of transcription, or a second
  transcription provider whose accepted list covers them — not a constant edit. If a deployment
  capture shows Meta sending `aac` for most voice notes, that work becomes the priority.

The taxonomy half was closed at the same time: a container outside V10's list is now
`AUDIO_FORMAT_UNSUPPORTED` (**400, not retryable**) rather than `TRANSCRIPTION_FAILED` (502,
retryable). The recording container is chosen by WhatsApp, so re-sending the identical voice note
fails identically forever, and Requirement 15.4's flag has to say so.
